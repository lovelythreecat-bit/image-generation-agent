# 独立图片 Agent 拆分可行性评估

日期：2026-09-28。结论：**可行，建议实施；按规则迁移、运行层重写开展，不能直接复制 worker。**

本轮交付评估与开发计划，没有实现产品代码，没有运行付费模型。原设计快照位于 `../specs/2026-09-28-standalone-image-agent-design.md`，当前实施规格为 [多图与接入修订设计](../specs/2026-09-28-multi-image-agent-revision-design.md)。优先级为修订设计 > 本评估第3节 > 原快照。用户要求按独立评审修正后，六项发现和三项建议已落实到文档，见 [修正记录](2026-09-28-review-resolution.md)；这不代表代码或真实模型已验收。原快照、来源manifest和独立评审正文保留。

## 1. 目标与方案

在 `F:\Work\电商\imageAgent` 建立独立 Python 项目，包名 `image_agent`，入口为异步 `create_images()` 和 `image-agent create`。支持主图、详情三镜头和拼多多白底图。保留商品核对、服装事实、平台合规、质检、单图一次修复；新增多图自动要素提取、按产物选择与追踪，素材不再限于单商品原图加风格图。提供 Python/CLI 与可序列化 DTO 接入契约，本期不开发 HTTP 服务或工作台。

| 方案 | 判断 |
| --- | --- |
| 复制规则和提示词，重写内存编排及 HTTP 层 | 推荐。保留已有创作规则，又能明确切断业务系统依赖 |
| 复制 worker 并模拟数据库、存储、租户接口 | 不采用。独立性差，隐藏依赖多，维护模拟接口没有价值 |
| 所有规则重新设计 | 不采用。工作量大，无法可靠保持与现有创作行为的对应关系 |

工作区本身就是新项目根目录，直接放 `pyproject.toml`、`src/image_agent/`、`tests/`，不再嵌套一层项目目录。首次评估时工作区为空且不是 Git 仓库（本轮现已有规划文档），开发开始时才初始化 Git 和独立虚拟环境。建议 Python >=3.12，与来源项目一致；运行时直接依赖仅 `httpx`、`pydantic`、`Pillow`。

## 3. 实施前固定的契约补充

以下是第一轮基线补充，继续保留协议/导出等细节。多图相关部分由修订设计覆盖：第3项首张风格规则仅限旧reference_images；第7项不能降级必需分析；第9项create_images新增analysis及analyze_materials；第10–11项取消清理、最终保存和output_errors按新规格8/6节；第11项落盘JSON与DTO区分。失败结果补ErrorInfo，镜头与required按新规格执行。其他冲突同样以修订设计为准。

1. **白底图尺寸特例。** `pdd_white_background` 先合成白底并导出 480×480 PNG，像素与视觉检查均用导出字节。它免除 768/1536/3000 通用长边下限；检查精确 480×480、大小 <3×1024×1024 字节、1:1 和白边。否则必然失败。白底图只为 pinduoduo 生成一次，不对所有平台做笛卡尔积。
2. **展示方式按资产生效。** 请求级展示方式控制主图、详情；白底图始终 product_only，忽略模特偏好。product_only 的服装融合与模特偏好分都归一为 100；避免 `product_only + female` 被无意义地判失败。结果的 presentation_mode 描述请求级解析结果；仅请求白底图时结果为 product_only。显式 product_only 不因原图观察而改成模特，auto 才可补救。
3. **白底参考例外。** 白底图沿用现有专用 worker：不传风格参考、不写 style_hint/style_prompt，避免场景污染。若请求提供参考图，准备阶段仍按设计分析全部参考，但白底资产不用它们。其他输出用首张参考作为生图和视觉质检参考。此项明确覆盖原设计“首张参考总进入生图”的宽泛表述。
4. **空类目仍拒绝。** 请求校验以 5.1 为准；自动占位只接受非空 `general/unknown/其他` 与自动名称组合。第 6 节提到空类目仅是来源逻辑的历史描述，不开放空输入。
5. **输出保持原始格式。** 主图/详情 image 字节不转码，PNG/JPEG 按文件头写 `.png/.jpg`，其他能被 Pillow 解码的图写 `.img`；白底为 PNG。覆盖第 4、6 节“全部写 PNG”的笼统描述。失败资产 image/file_path 为 None，只保留错误、最终提示词和最后一次可用质检 JSON。
6. **HTTP 与创作重试分开。** HTTP 总尝试 3 次，等待 2、4 秒，状态仅 429/502/503/504，加 ConnectError/ConnectTimeout/ReadTimeout/WriteTimeout。无图、坏 JSON/schema、非法 base64 是协议失败，不做额外创作重试。可解码生成图的像素或分数不达标才进入一次 strict/staged 修复；坏图字节、白底转换异常直接失败。staged 最多是初次出图 + 场景图 + 融合图共 3 次生图逻辑调用，每次仍可能有 HTTP 重试。
7. **视觉失败不能默许成功。** 原图核对请求或 schema 失败：返回 failed、assets=[]，input_check.matches=false，reason 明确写“核对服务失败”而非“商品不一致”。单图质检或一致性复核服务失败：该资产 failed，不重新生图；保留已有质量信息。服装/风格失败：warnings 并继续。成组检查失败：记录带 platform、passed=false、error 的审计，分数为 None，不改变资产状态。
8. **风格响应统一结构。** 风格聊天要求 JSON `{"style_prompt":"..."}` 并做 Pydantic 校验，再应用原文完整性检查。目标 60–100 词，接受条件仍为至少 20 词、完整句尾、非残缺尾词。首模型内容不完整或 schema 失败可试不同的质检模型一次；传输失败耗尽则警告并继续。两模型相同不重复调用。
9. **测试注入不改变公共入口。** 保留 `create_images(request, config=None)`。内部 `run_pipeline(request, config, *, dependencies)` 接受协议替身；公共入口负责建立/关闭真实客户端。低层 HTTP 用 httpx.MockTransport。AgentConfig 只包含配置数据；测试无需真实密钥、网络和原项目环境。
10. **独立 HTTP 和并发。** 使用专属 AsyncClient，`trust_env=False`，只使用 IMAGE_AGENT_HTTP_PROXY，不自动加载任何 `.env`。每个真实图片模型共享进程内并发上限，多个别名指向同模型时共用额度；实现须支持多个 asyncio.run 的生命周期，不复用绑定旧 loop 的 Semaphore。并发配置不同但指向同模型的重叠请求直接配置报错，避免上限含义不确定。取消任务必须释放额度、向上传播，不能转换为普通失败。
11. **文件名及重名。** request_id 只接受 Windows 可用的单个路径组件，拒绝路径分隔符、`..`、绝对路径、保留设备名、尾随空格/点。目标为 output_dir/(request_id 或 create)，已存在即抛 OutputError，不覆盖；在模型调用前以独占 mkdir 预留。无 output_dir 不创建目录。成功文件写入失败时保留内存成功资产和 warning、file_path=None；result.json 无法写入抛 OutputError，并携带完整 result 供 Python 调用方取回。CLI 遇写盘错误退出 1。JSON 的 image/file_path 均为相对路径或 None，绝不塞 base64。
12. **重复项及优先级。** 平台 trim+小写后按首次出现去重；输出类型去重；生成仍按主图→详情→白底固定排序。显式 aspect_ratio 对主图/详情优先于模板默认比例，增加最后的比例覆盖指令并向审核明确同一目标比例。平台规则文本本体保持来源版本。strict 的“完整商品”要求对 closeup/feature 按镜头裁切意图解释，不能强迫特写变全身。
13. **合规兼容边界。** 保留市场数字全串替换，包括它对商品数字/结构 JSON 的影响，并在 README 说明。危险词检查只扫未追加平台指令的提示词；例如平台文本自身含 `fake badge` 不应造成所有拼多多图被拦截。重试文案也不得改变这一顺序。白底“无白边距”文案与白边检测保持原规则兼容，理解为不加装饰边框；真实样本中需检查其实际效果。
14. **文档引用修正。** 原第 6 节“按第 10 节重试”应读第 8 节；第 8 节 HTTP 重试引用应读第 4 条第 6 项。隔离检查针对运行时代码 import、依赖声明和配置读取，允许文档、许可、来源清单出现 MediaForge。

## 4. 风险与验证范围

- 工程复杂度中等偏高，集中在重试分类、视觉调用失败边界、白底特例；规则迁移本身风险较低。
- 本轮仅静态核对 `/images`、模型名与请求格式在源码中存在，未验证供应商当前可用性或账号权限。模型默认值照设计保留且可配置；不能宣称三款模型已经实测可用。
- 生图与视觉打分具有随机性；离线测试只能证明逻辑、参数与状态正确，不能保证商品一致性或上架合规。平台规则是来源快照，未做平台官方政策更新审计。
- 全部 9 平台请求主图+详情+白底，共 9+27+1=37 个资产。全走 strict 最多 74 次生图逻辑调用；允许 staged 的全部走 staged 时最高 109 次（35×3+2×2），不含质检和 HTTP 重试。内部串行，总时长可能较长；首版不额外提供实时进度或成本核算。
- Windows 环境中裸 `python` 命令当前指向不可用入口；已发现 uv，但其默认缓存受沙箱权限限制。本轮没有安装依赖或完成环境验收。开发第一个任务明确建立工作区内环境并验证 Python 3.12。
- 不读、不改原项目 `.env`、数据库或服务；来源项目保持运行。来源代码变化手工同步，无双向 import。

## 5. 工作量与验收

修订为 10 个可独立验收的任务（原 8 个任务加 5A 多图选择、7A 第三方契约），按依赖顺序实现，详见 `../plans/2026-09-28-standalone-image-agent.md`。人工工程估算约 10–15 个工作日（原范围 6–9 天，多图与接入增加 4–6 天，含离线测试、审查和文档），作为排期量级，不是自动执行耗时承诺；真实模型调试单独按结果评估。

验收分两层：必须通过独立安装、无网络测试、依赖隔离、Python/CLI 和输出契约；真实调用用明确指定图片、模型和资产数量的手工脚本验收。未进行真实调用时交付说明必须明确这一点。

## 6. 本轮需求修订评估

多图与第三方接入可行，但不能仅把 product_image 改成列表。需要可检查的素材分析、跨图主体归并、按资产选择及多来源审核。默认自动选取与需求相关的主体/要素，输入角色与要素提示均可选；主商品不明确、身份冲突或缺必需证据时返回 needs_input，调用方修订请求再调用。多个候选商品不默认全入图，同商品正反面也不要求每个细节在每个镜头都可见。

新增 MaterialAnalysis、AssetElementPlan、逐主体及逐必需要素审核；图片与要素 ID 进入产物追踪。可选背景与白底冲突仅排除该资产背景，必需要素与平台冲突仅让对应资产失败。默认新路径输入 1–8 张，生图参考上限按配置声明（默认 4），不足以覆盖必需证据不静默截断。供应商是否真支持声明容量须真实验收，源码协议可发送多图不等于模型效果已验证。

推荐稳定 JSON DTO 加内存字节 bundle；外部 media_id 由接入 adapter 解析，核心无用户/租户/任务状态。本期只交付轻量转换接口、schema 和无框架示例，不搭 HTTP 服务或工作台。两阶段分析结果可以展示并选取，但回传快照不是可信的已审核证明；核心仍以素材核对已选主体和必需证据。

新增风险主要是自动识别主商品、错误归并不同型号、配件误当必选商品、要素遗漏和视觉上下文上限。保持原 37 资产/最多 109 次生图的上界（修复次数未增加），准备与逐主体审核会增加视觉调用和 token；不得沿用原单图成本估算。真实验收新增多视角商品、商品+细节+背景、明确多对象与冲突素材案例，并结合人工观察，不以模型评分代替效果验收。

评审后的具体约束：发现模型同时输出结构化意图，选择层只作确定性应用；原子事实内来源可替代、跨必需事实共同覆盖；explicit/brief required为每资产要求；澄清采用draft→证据核对→finalize；failed/partial与异常统一ErrorInfo；初审same_product=false即使高分也失败。供应商协议检查前移任务3，取消无后台遗留写盘。非服装无风格、淘宝四资产的基准为10次逻辑调用，两阶段为11次，其余视觉与HTTP重试另计。均已进入原十任务验收，不增加工作台、服务或计费模块。
