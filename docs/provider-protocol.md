# Provider protocol checkpoint — 2026-09-29

## Deployment boundary

`AgentConfig.from_mapping()` and `from_file()` share typed validation. Configuration
sources stay outside the pipeline; database callers pass an already-read mapping.
Named services own base URL, key source, protocol and endpoint paths. Image aliases
bind a service before generation, so equal model names on different hosts cannot
select the wrong credentials. Vision methods resolve their own stage route.
The shared HTTP client attaches authorization per request and never follows redirects.
No provider/key fallback is introduced. Multipart uses the existing retry and error
redaction policy; reference bodies are bytes and replayable on transport retries.

Evidence validation sends explicit subject, required-fact and pending-issue ID lists.
Every listed ID must appear exactly once; other snapshot facts remain context only.
Vision response format/schema errors and evidence/generated-audit ID mismatches
share at most one corrective call per vision stage on the same route, with the same
encoded images and field/ID diagnostics. A second invalid response fails closed.
HTTP/transport errors retain their own policy; refusals and valid negative verdicts
do not trigger schema repair. The client never invents missing checks, drops unknown
audit fields, or changes verdicts locally. JSON objects, JSON text, text-block arrays
and a single JSON Markdown fence are parsed before strict schema validation.
Final errors include the vision stage, schema name and up to six failing field
locations/types; raw response values are excluded.

Generated bytes that have passed decoding are retained if later auditing or repair
fails. Such assets remain failed and are saved under candidates/ rather than the
approved output directories. The desktop previews them with a persistent unapproved
notice. Third-party result bundles still include only succeeded image blobs.
Schema correction never regenerates the image; candidate retention does not turn
an audit failure into success.

## OpenAI official GPT Image 2

References (retrieved 2026-09-29):
- https://developers.openai.com/api/docs/models/gpt-image-2.md
- https://developers.openai.com/api/docs/guides/image-generation.md

`openai_images` sends references to POST `/v1/images/edits`: multipart `image[]`
files in evidence order, `model`, `prompt`, `n=1`, `quality`, `size`. With no
references it sends JSON to `/v1/images/generations`. The prompt retains numbered
reference roles. Inputs are the existing JPEG-encoded references. GPT Image 2 has
always-high input fidelity; `input_fidelity` is omitted. Responses use `data[].b64_json`.

GPT Image 2 quality tiers are low/medium/high for 1K/2K/4K, independent of canvas.
Canvas dimensions are exact-ratio multiples of 16, around 1024 long edge and at
least 655360 total pixels; maximum 3840 long edge and 8294400 pixels. Aspect ratios
over 3:1 fail locally as capability errors (including the request contract's 4:1
and 1:4). Default main 1:1 maps to 1024x1024; detail 3:4 maps to 768x1024.
Other models/services must implement this selected wire contract and size policy;
model naming alone is not automatic capability discovery.

`chat_completions` uses the existing JSON image data URLs and
`response_format={"type":"json_object"}`. The official example uses gpt-4o-mini.
All named vision methods may override the default vision route. Structured style
routes fail explicitly without the legacy style-to-quality model fallback.

The official example and complete pipeline are tested with `httpx.MockTransport`.
No official billable test has run; account access, results, latency and billing
remain unverified. OpenRouter's observed discovery-stage HTTP 403 is not resolved
by these offline protocol changes.

## OpenRouter

Read-only reference: https://openrouter.ai/docs/guides/overview/multimodal/image-generation (retrieved 2026-09-29).

The official guide describes POST `/api/v1/images`, `model`, `prompt`, `n`, `input_references`, `resolution` tiers including 1K/2K/4K, and `aspect_ratio`. Its GPT Image 2 example uses `quality: high`, `aspect_ratio: 16:9`, `n: 1`. The guide exposes `/api/v1/images/models` and per-model `/endpoints` for capability discovery. This agrees with the reviewed source protocol and the package's request envelope.

Implementation prefers non-empty `data[].b64_json`, then inline images in
`choices[].message.images` and `message.content`. With no inline image, the generator
downloads a supplier `data[].url` or chat image URL. An empty/whitespace `b64_json`
with a sibling URL is treated as URL output; malformed non-empty Base64 still fails.
This handles the observed PenguinAPI response with `b64_json: ""` and a non-empty URL.
Invalid JSON/schema/base64 does not trigger extra creative retries.

Downloads reuse the configured proxy/timeout but send no API authorization, default
client headers, auth, or cookies, including after redirects. HTTP(S) URLs must have
no embedded credentials; localhost and non-global literal IP addresses are rejected.
Redirects are checked at each hop and limited to five. Downloaded content is capped
at 32 MiB, including streaming bodies without Content-Length, and decoded as an image
before use. Existing transient retry rules apply to GET only; downloading never
resubmits generation. Download errors omit signed URLs and response bodies.

Image decoding errors include the field location, value type/length, and a content-free
format classification (empty, non-string, data URL, remote URL, whitespace, or invalid
encoding). The generator appends the configured host, endpoint path, protocol, model,
body format and reference count. The same diagnostics flow into the existing asset
error and result JSON, and the desktop selects a failed asset when no image is available.
Raw response values, signed image URLs, image bytes and credentials are not logged.
The synchronous `extract_image_bytes` helper remains inline-only; the async generator
owns the URL-download path. Live supplier access is not covered by offline regressions.

Not verified: account access, default model availability, actual multi-reference limits for each endpoint, whether every selected fact is retained, quality, latency, billing, and results with 4/8 source images. Generation/vision limits are deployment declarations, not measured provider guarantees. No billable request has been made. `scripts/live_smoke.py --live` is the separate opt-in acceptance path.
