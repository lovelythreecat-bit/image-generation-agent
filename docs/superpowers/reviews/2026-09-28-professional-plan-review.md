# 独立图片 Agent 开发计划专业审查

日期：2026-09-28。审查角色：独立子 Agent。

**结论：修订后实施。** 多图创作与独立接入方向可行，模块划分、单资产修复和 DTO/图片字节分离基本合理；不需要推翻方案或增加工作台、任务服务。目前不宜直接按计划冻结第一版数据模型：有 2 项阻塞级契约缺口、4 项重要缺口，集中在“模型理解如何变成确定性选择”“多视角证据如何覆盖要求”及结果判定，容易导致实现中返工。

本轮仅为静态设计与计划审查。阅读修订规格、开发计划、可行性评估、原设计快照及来源生图协议实现；未实现或运行产品代码，未运行测试、真实模型或付费调用，未修改被审查文档。下列行号以本轮读取版本为准。“阻塞”表示应在冻结共享模型前修订，不表示功能无法实现。

## 阻塞级发现

### B1. 自动选择承担语义理解，但没有接收结构化意图的接口

**位置：** 修订规格第 55、59–83 行；计划第 193、195、216–221 行。

`resolve_selection` 被定义为不调用模型的纯函数，却要判断任意 `creative_brief` 是否要求组合、哪些细节与需求相关、哪个商品是主体。`MaterialAnalysis` 目前只有观察、主体、要素和问题，没有结构化的意图解析、建议主体/要素选择或语义关系；`Subject` 也只列出 ID、素材、身份事实和商品匹配。第 94 行要求的“最清晰代表图”同样缺少可消费的字段。

**触发例子：** 两张图分别是杯子和杯盖，brief 为“盖子放在杯子旁边展示，别扣上”。图片观察和 `matches_product` 无法让纯函数可靠推出共同呈现、相对关系、杯盖是配件还是第二主体。若临时采用关键词判断，会把自然语言理解重新藏进 selection；若再次询问模型，又违背目前的调用边界与成本约定。只提供已选好主体的 fake 不能验证这一缺口。

**最小修正：** 由现有的一次视觉发现同时产出结构化 `IntentAnalysis`/`SelectionProposal`，至少包含建议主主体、共同呈现对象、要素优先级、关系约束、未满足要求和代表素材 ID；显式选择覆盖哪些建议也需固定。selection 只做 ID 闭合、约束校验和平台规则应用，不新增模型调用。关系约束可先保持少量类型加文本，不必设计通用场景图框架。

**验收补充：** 给完整分析响应 fixture，再从该响应运行真实 selection，覆盖否定组合、杯与盖分开放置、背景内其他商品不入选；不要在测试替身中预先替 selection 做完决策。

### B2. evidence 列表未定义“替代证据”与“共同必需证据”，无法可靠计算参考覆盖

**位置：** 修订规格第 65、70–76、92–96 行；计划第 76、216、219、221 行。

参考编译要按 required 要素做贪心覆盖，但一个 Element 的 `evidence` 是平铺列表：列表中的图片究竟任选一张即可证明该要素，还是必须共同提供不同事实，没有约定。`Subject.identity_facts` 也没有明确逐事实的证据链接。仅验证引用属于输入集合，并不能计算覆盖关系。

**触发例子：** 同一背包的正面商标和背面拉链被模型汇总成一个身份/结构 Element，证据含正面图 A 与背面图 B。若任一 evidence 即算覆盖，选 A 后会把 B 丢掉，仍声称 required 已覆盖；若一律要求全部 evidence，同一商标的五张重复视角又会错误耗尽默认四个参考位。

**最小修正：** 明确原子事实或原子要素的粒度，并规定一个事实内证据为可替代来源、不同 required 事实之间为共同要求；复合要素拆成事实集合。主体身份也须引用这些事实。将“生成必须带哪些证据”与“审核为发现矛盾而查看哪些图”区分开，保留现有贪心策略即可，无需优化求解器。

**验收补充：** 同一事实五张替代图只需一个槽；正面标志与背面拉链两个 required 事实必须各有覆盖；一张图支撑两事实可去重；不足时资产级失败。测试应从上述证据结构计算，不手填已完成的参考列表。

## 重要发现

### I1. 镜头可见范围与 required 优先级没有落到字段和判定规则

**位置：** 修订规格第 92、104、112 行；计划第 76、80、186、219 行。

规格允许特写把其他主体标记为不适用，同时规定已选主体/required 必须保留。`AssetElementPlan` 的已列字段没有逐主体/逐要素的可见性、焦点或要求来源；审核结果却允许 `not_applicable`。尚不明确这是由计划决定，还是模型事后声明，也未区分默认身份要求与用户明确必需的要求。

**触发例子：** 用户明确 required“杯子旁边展示杯盖”，closeup 只拍杯壁，模型把杯盖标为 `not_applicable`。当前约定既可能让这张图通过，也可能判缺要素；若所有镜头都这样豁免，最终整组产物也可能从未出现杯盖，而成组检查又不改变成功状态。

**最小修正：** 给计划增加逐项 applicability/visible requirement 及其来源（默认身份、用户必需、镜头规则），固定 required 是每资产要求还是整组覆盖要求。第一版可采用简单的每资产语义：明确 required 不允许由模型自行转成不适用；不能满足镜头时在编译期失败或调整焦点。默认身份事实可按确定的镜头规则豁免。若选择整组语义，则必须补上覆盖验收，不能继续只报告。

**验收补充：** 计划要求可见、模型却返回 `not_applicable` 时必须失败；合理背面/特写不因不可见正面细节误失败；用户显式 required 的要素不能在所有资产中被豁免。

### I2. 旧冲突快照的澄清恢复路径没有完整定义

**位置：** 修订规格第 83、88 行；计划第 77、216、218、242 行。

规格承诺 explicit 可解除选择歧义，身份冲突须重新核对；但流水线先 `resolve_selection`，其未通过就终止，之后才执行快照 `validate_evidence`。当前没有区分“旧问题已被本次选择排除”“仍需复核的问题”和“确定阻断的问题”，也没有说明 `Issue.options.id` 如何提交回选择。若 resolve_selection 沿用旧冲突，证据复核永远无法发生；若把所有冲突忽略，又可能放过仍被选中的矛盾事实。

**触发例子：** 快照把红款/蓝款混为一组并返回冲突；用户选择明确的红款候选或排除蓝款要素后重提。实现需要确定候选是否足以表达这次选择，以及哪些证据仍须核对，而不能仅根据旧 status 提前失败。

**最小修正：** 明确两段处理：先解析合法的候选选择并保留待复核问题；复核后再决定 ready/needs_input/failed。问题需能关联主体/事实并说明可用的解除动作；简单情况下让 options 明确映射 subject_ids/element_ids 即可。不能在现有候选上解除的冲突，明确要求修订素材重新分析。

**验收补充：** analyze 返回 needs_input → explicit 选择 → 必要证据复核 → create 成功；仍有矛盾时零生图；非法 ID 直接拒绝。当前测试主要检查返回 needs_input 和篡改失败，缺少恢复的完整正向链路。

### I3. 对外承诺结构化供应商错误，但结果仍继承字符串错误

**位置：** 原设计第 115 行（`Asset.error: str | None`）；修订规格第 110、114、132 行；计划第 82、244、276–280 行。

新增 ErrorDTO 针对异常转换，规格另要求 ProviderError.kind 保留在结果错误中。但大多数供应商错误在流水线内被捕获，变成 failed/partial 资产；准备失败则返回 assets=[]。当前没有为 Asset 或 CreationResult 定义结构化错误承载字段，因此 `error_to_dto` 不一定能接收到这些异常，接入方最终仍只能解析中文字符串。

**触发例子：** 两张图分别因超时和参考容量不足失败，第三方应能显示不同处理建议，却从相同的 failed 状态与自由文本无法可靠区分 retryable、capability、protocol。素材分析服务失败的整单结果也缺少同等机器可读字段。

**最小修正：** 保留旧 error 文本，同时新增结果级/资产级统一 ErrorInfo（code、kind、retryable、message，必要时 status_code）。由捕获异常的位置构造，ErrorDTO 复用同一映射规则。无需扩展 HTTP 服务。

**验收补充：** partial 中不同错误类型、准备阶段 ProviderError、普通抛出异常三条路径，经过 result_to_bundle/error_to_dto 后仍保留一致的 code/kind/retryable，且不回显原始输入或凭证。

### I4. 初审 same_product 与高分冲突时没有通过规则

**位置：** 计划第 80、186–187 行；修订规格第 104–106 行。

GeneratedImageAudit 的 subject_checks 同时含 score 和 same_product，但通过规则只写初审身份分数 >=85；只有聚焦复核明确要求 same_product=true。Pydantic 能校验字段类型，不能自动阻止 `{score:95, same_product:false}` 这类语义冲突。

**触发例子：** 模型给出高相似度分数，同时认为是相近的另一个型号。若只按 score 评分，资产会直接成功，也不会触发 80–84 的复核。这违反商品身份必须保持的要求。

**最小修正：** 明确初审也要求每个可见主体 same_product=true 且 score 达线，或将高分/否定身份组合定义为协议矛盾并失败；选一种规则固定即可。逐主体结果还应校验 ID 唯一、必需集合完整，不能用重复同 ID 掩盖漏审。

**验收补充：** 初审 95/false、85/true、84/true、多主体重复 ID/漏 ID、复核不覆盖 required 细节失败。具体走质量修复还是协议失败须与选定规则一致。

## 建议与可延期内容

1. **把协议可用性检查前移，实际调用仍单独授权与验收。** 计划第 295 行把真实模型验收放到最后。源码只能证明曾构造两参考图的 payload。建议在任务 3 完成后设置一个明确的供应商风险检查点，核对当前 `/images`、参考字段、模型容量和响应形式；若尚不做真实调用，至少把“仅完成离线协议实现”写进里程碑，不能将四参考图 fake 当作真实能力证据。无需自动模型探测或供应商注册框架。

2. **补一条取消/落盘的生命周期约定。** 计划第 185 行要求编码使用 `asyncio.to_thread`，第 228、268 行由公共入口预留目录、最终保存结果，第 246 行要求取消传播。线程工作不能仅靠取消 await 强行停止，且长流程取消后可能留下预留目录。明确取消时是否写入任何已完成结果、预留目录保留规则和下一次需要新 request_id；增加一次取消时无悬挂客户端/许可、无未跟踪写盘的测试即可。不需要断点续跑或任务持久化。

3. **成本估算保留上界，但标明调用类别。** 原 37 资产、最多 109 次生图逻辑调用的算术成立；它不包含准备、逐图审核、聚焦复核、成组审核和 HTTP 重试。两阶段调用也不是免费复用分析。README 给一个“单平台四资产、无修复”案例的调用账单即可；运行时成本计费、进度推送、缓存签名和分批聚类均可延期。

## 架构与复杂度评价

- 合理：pipeline 唯一编排、规则/传输/选择/输出拆分、成功资产不重复生成、传输错误与质量修复分层，均能控制多图带来的复杂性。旧接口归一化而非维护两套流水线也正确。
- 多图必需的新增工作：主体归并、事实证据、镜头适用性和按资产参考容量不能省略。B1/B2 的修正应落在现有分析响应与共享类型中，不应再引入第二套 Agent 框架。
- 接入边界合适：Python API、JSON Schema、media_id 显式绑定和 blob bundle 已足以让第三方封装工作台；本期不需要上传服务、鉴权、队列或云存储。
- 测试结构可实施：MockTransport、真实 Pillow 样本、公共 API 冒烟和独立 wheel 安装有价值。但模型 fixture 只能证明消费响应的逻辑，不能证明多对象识别准确；核心分析到选择到计划的串联用例应使用真实选择函数，避免把关键缺口藏在 fake 中。
- 10–15 人日可作离线工程量级估算，目前不宜理解为固定承诺。共享结构冻结前解决以上缺口，比在任务 5A/6 再修改 schema、提示词、DTO 和测试更省工作。真实模型效果仍须人工样例验收。

2. 固定澄清恢复状态转换、结构化结果错误、初审身份布尔值规则（I2、I3、I4）。
3. 给任务 1、4、5、5A、6、7A 补上述针对性验收，再按原顺序实施；不需要重排全部十项任务。
